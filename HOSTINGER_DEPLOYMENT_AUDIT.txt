STEP PLATFORM - HOSTINGER LIVE DEMO GUIDE
==========================================

Project: STEP Platform
Stack: Laravel 12, PHP 8.2+, React 18, Inertia.js, Vite, MySQL/MariaDB
Target: Hostinger shared hosting for controlled demo testing
Status: DEPLOYMENT PREPARATION GUIDE - NOT A PRODUCTION SECURITY APPROVAL

This guide is specific to the current repository. It assumes a fresh Hostinger
database and a domain or subdomain with HTTPS enabled. Do not use real student,
financial, identity, or confidential documents for an unreviewed demo.


1. GO / NO-GO CHECK
-------------------

Do not make the site publicly discoverable until all items marked BLOCKER are
complete.

BLOCKER - rotate every credential that has appeared in local environment files.
This includes SMTP passwords, Supabase service-role/S3 credentials, and any API
keys. The current local .env contains secret values. Never upload it to Hostinger.

BLOCKER - create a separate demo database and demo credentials. Do not import
the local database or SQL dumps without reviewing and sanitizing their data.

BLOCKER - set APP_ENV=production and APP_DEBUG=false on Hostinger.

BLOCKER - review and protect the API routes in routes/api.php. Ledger, project,
onboarding, concern, OTP, and password-reset operations need authentication,
authorization, and throttling appropriate to each endpoint.

BLOCKER - remove OTP values from logs and replace API responses that expose raw
exception messages with generic client messages. Keep technical details in logs.

BLOCKER - decide whether proof documents may be public. The current application
uses the public storage disk in several project/ledger paths. For real documents,
use private storage and authorized download responses before going live.

The application is otherwise compatible with Hostinger's expected runtime:
Composer metadata is valid, PHP 8.4 works locally, the Vite production build
succeeds, and the repository contains an ordered Laravel migration baseline.


2. HOSTINGER REQUIREMENTS
-------------------------

Confirm these features in the selected Hostinger plan before uploading:

- PHP 8.2 or newer; PHP 8.4 is preferred if available
- MySQL or MariaDB with pdo_mysql
- PHP extensions: mbstring, openssl, fileinfo, xml, curl, and bcmath
- Apache mod_rewrite and .htaccess overrides
- HTTPS certificate for the demo domain
- SSH or Hostinger terminal access, if available
- Cron jobs for database queue processing
- PHP upload and post limits large enough for the allowed proof files

The application should run on shared hosting, but it is not the same as a
persistent VPS process. Do not depend on a permanently running queue worker.


3. PREPARE THE REPOSITORY LOCALLY
----------------------------------

Run these commands from the project root. Do not run the production setup script;
it can generate keys and migrate using the wrong environment.

    composer validate --no-check-publish
    composer install --no-dev --prefer-dist --optimize-autoloader
    npm ci
    npm run build

The production frontend is written to public/build. It is ignored by Git, so
either build it on Hostinger or upload the generated public/build directory.
Do not upload node_modules, local .env files, cookies.txt, or unsanitized SQL
dumps.

Before upload, inspect the files that will be transferred and confirm that they
do not contain credentials, personal data, or authentication cookies.


4. CREATE THE HOSTINGER DATABASE
---------------------------------

In hPanel:

1. Create a new MySQL database, user, and strong password.
2. Grant the user full access to that database.
3. Record the database name, username, password, and Hostinger database host.
4. Use a fresh database for the demo.

The repository currently has ordered migrations for the core application tables,
sessions, personal access tokens, push subscriptions, identity verification,
date-change requests, and notification reads. Verify the exact migration state
after deployment instead of blindly importing one of the SQL files.

If existing demo data is required, take a backup first and sanitize users,
passwords, tokens, audit logs, uploaded-file paths, and other personal data.


5. UPLOAD THE APPLICATION
-------------------------

Preferred layout:

    /home/account/step22/                 Laravel project root
    /home/account/domains/example.com/public_html/  document root

Configure the domain document root to point directly to:

    /home/account/step22/public

Keep .env, app, bootstrap, config, database, resources, storage, and vendor
outside the public web root. Do not expose the project root through a second
domain or directory listing.

If the Hostinger plan cannot point a domain to public/, copy only the contents
of public/ into public_html and update public_html/index.php paths to the actual
project root. Do not copy the whole Laravel project into public_html without
protecting the non-public directories.


6. CREATE THE PRODUCTION .ENV ON HOSTINGER
-------------------------------------------

Create the file directly in the Laravel project root. Replace every placeholder.
Do not paste values from the local .env.

    APP_NAME="STEP Platform"
    APP_ENV=production
    APP_KEY=base64:GENERATE_A_NEW_KEY
    APP_DEBUG=false
    APP_URL=https://demo.example.com

    LOG_CHANNEL=stack
    LOG_STACK=single
    LOG_LEVEL=warning

    DB_CONNECTION=mysql
    DB_HOST=HOSTINGER_DB_HOST
    DB_PORT=3306
    DB_DATABASE=HOSTINGER_DB_NAME
    DB_USERNAME=HOSTINGER_DB_USER
    DB_PASSWORD=HOSTINGER_DB_PASSWORD

    SESSION_DRIVER=database
    SESSION_LIFETIME=120
    SESSION_ENCRYPT=true
    SESSION_SECURE_COOKIE=true
    SESSION_HTTP_ONLY=true
    SESSION_SAME_SITE=lax

    FILESYSTEM_DISK=local
    CACHE_STORE=file
    QUEUE_CONNECTION=database

    MAIL_MAILER=smtp
    MAIL_HOST=SMTP_HOST
    MAIL_PORT=587
    MAIL_USERNAME=SMTP_USERNAME
    MAIL_PASSWORD=NEW_SMTP_PASSWORD
    MAIL_ENCRYPTION=tls
    MAIL_FROM_ADDRESS=verified-sender@example.com
    MAIL_FROM_NAME="STEP Platform"

    VITE_APP_NAME="${APP_NAME}"
    VITE_SUPABASE_URL=https://your-project.supabase.co
    VITE_SUPABASE_ANON_KEY=YOUR_PUBLIC_ANON_KEY
    SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVER_ONLY_KEY

Do not put SUPABASE_SERVICE_ROLE_KEY, SMTP passwords, or S3 secrets in any
VITE_ variable. VITE_ values are available to browser code after building.

Generate a new key only for a new demo environment:

    php artisan key:generate --show

Changing APP_KEY later can invalidate encrypted cookies and other encrypted
data, so record the production key securely and do not rotate it casually.


7. INSTALL AND INITIALIZE LARAVEL
---------------------------------

From the Laravel project root, run:

    composer install --no-dev --prefer-dist --optimize-autoloader
    php artisan optimize:clear
    php artisan migrate:status
    php artisan migrate --force
    php artisan storage:link
    php artisan config:cache
    php artisan route:cache
    php artisan view:cache

If composer is unavailable on the plan, build vendor locally with the same PHP
major/minor compatibility and upload vendor. Prefer Hostinger SSH/Composer when
available so platform extensions are detected correctly.

The database-backed session and queue drivers require these tables to exist:

- migrations
- sessions
- jobs
- failed_jobs
- job_batches

The current repository has a sessions migration but no migration that creates
jobs, failed_jobs, or job_batches. Before enabling queued mail, create and run
the queue-table migration on the demo database:

    php artisan make:queue-table
    php artisan migrate --force

Confirm all five tables exist before testing queued mail. Keep the generated
queue migration in the repository so future deployments use the same schema.

Ensure the web process can write to storage and bootstrap/cache. Never make
.env writable from the browser.


8. QUEUES, EMAIL, AND CRON
--------------------------

Queued mail will not be delivered until a worker processes the database queue.
Create a Hostinger cron job from the Laravel project root. Use the PHP binary
shown by Hostinger; the exact path varies by plan.

    /path/to/php artisan queue:work --stop-when-empty --tries=3

Run it every minute or at the smallest useful interval supported by the plan.
For a low-volume demo, --stop-when-empty lets each cron invocation finish.

Monitor failures with:

    php artisan queue:failed

Test OTP, verification, password reset, welcome, and notification mail using a
demo account. Configure SPF/DKIM/DMARC for the sending domain where possible.


9. SUPABASE CHECKLIST
---------------------

The email function must read the secret by its environment-variable name:

    Deno.env.get("RESEND_API_KEY")

Configure the secret in Supabase, deploy the function, and verify its caller
authentication, CORS policy, and rate limits. Do not place a Resend or Supabase
service key in frontend code.

Use private Supabase Storage buckets and signed URLs for sensitive documents.
Review the bucket policies before testing uploads.


10. FIRST-DAY SMOKE TEST
------------------------

Perform these tests over HTTPS after clearing and caching configuration:

- Homepage, Inertia navigation, CSS, JavaScript, and images
- Registration, OTP send/verify, email verification, and password reset
- Login, logout, session persistence, CSRF, and secure cookies
- Student, teacher, CSG, adviser, and superadmin dashboards
- Role-restricted pages and API requests using each demo role
- Project create, read, update, delete, and ownership authorization
- Ledger entry creation, proof upload, approval, correction, and deletion checks
- Chain verification and project access boundaries
- Notifications and mark-as-read ownership checks
- Queued email delivery and failed-job reporting
- Supabase OAuth, functions, and storage policies
- HTTPS redirect, custom 404/500 responses, and application logs
- File upload size/type limits and storage permissions

Use browser developer tools and Hostinger logs to check for failed asset URLs,
mixed-content warnings, 419 CSRF responses, 500 errors, and blocked SMTP calls.


11. ROLLBACK AND OPERATIONS
---------------------------

Before migrations or data imports:

1. Export a Hostinger database backup.
2. Keep the previous application release available.
3. Record the current .env configuration securely.
4. Put the site in maintenance mode if a data migration requires downtime.

After launch, monitor storage usage, application logs, failed jobs, SMTP
delivery, database size, and backup completion. Remove demo accounts and files
before sharing the URL outside the intended test group.


12. DEPLOYMENT ORDER SUMMARY
----------------------------

1. Rotate exposed credentials and create demo-only secrets.
2. Finish API authorization, rate limiting, error redaction, OTP-log removal,
   and private-file decisions.
3. Create a fresh Hostinger database and sanitize any imported demo data.
4. Build the frontend and upload the application with public/ as document root.
5. Create the production .env directly on Hostinger.
6. Install Composer dependencies and run migrations.
7. Create the storage link, permissions, HTTPS, and queue cron job.
8. Configure SMTP and Supabase secrets/functions.
9. Cache Laravel configuration, routes, and views.
10. Run the smoke tests and monitor the demo before wider access.
